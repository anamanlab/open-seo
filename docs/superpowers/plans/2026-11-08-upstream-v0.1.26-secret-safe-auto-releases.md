# Upstream v0.1.26 Upgrade + Secret-Safe Automatic Releases Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take `anamanlab/open-seo` from its v0.1.6 base to upstream `v0.1.26` without losing Google Search Console/GA4 grants or production configuration, then make upstream releases flow through a guarded, automated sync → CI → risk-classified deploy → verify pipeline.

**Architecture:** Merge upstream release tags into `main` in an isolated worktree and keep a small, documented fork-patch set. Put the OAuth-critical secrets in Cloudflare Secrets Store bindings, keep the remaining values as preflighted Worker Secrets, and guard every deploy with SHA-256 fingerprints plus binding/resource verification. Upstream sync and deployment are separate GitHub Actions workflows, so a merge can never deploy without CI. A fail-closed classifier labels each release `risk:low` or `risk:high`: low-risk releases deploy unattended, high-risk releases pause at a protected GitHub Environment for operator approval.

**Tech Stack:** GitHub Actions, Git worktrees + merge commits, pnpm 10, Node 22, TanStack Start, Cloudflare Workers/D1/KV/R2/Durable Objects/Workflows, Alchemy v2, Wrangler 4, Cloudflare Secrets Store, Vitest, oxlint, Prettier, knip.

**Spec:** User request 2026-11-08; `docs/GOOGLE_CONNECTION_STABILITY_PLAN.md`; `docs/SELF_HOSTING_CLOUDFLARE.md`; `docs/SELF_HOSTING_CLOUDFLARE_OPERATIONS.md`.

## Global Constraints

- Never print, commit, log, or paste secret values. The fork is public; GitHub Actions logs are public.
- `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` must be the **original production values** recovered above. Never generate replacements.
- `BETTER_AUTH_SECRET` is **not recoverable** and must be preserved as an inherited Worker Secret. Never rotate or replace it. If it is ever lost, every GSC/GA4 grant breaks and all 5 projects require re-consent.
- Preserve the existing `TEAM_DOMAIN`, `POLICY_AUD`, `ACCESS_ALLOWED_EMAILS`, custom domain, and D1/KV/R2 resource IDs. `POLICY_AUD` is a plaintext Worker var and must be pinned explicitly (see Task 0.2 Step 4).
- Production deploy policy (operator decision, 2026-11-08): **low-risk releases deploy automatically; high-risk releases require approval** in the `production` GitHub Environment. "Low-risk" is defined by the classifier in Task 2.1, not by whoever triggered the run. Ordinary human merges default to high-risk.
- Every deploy still requires a fresh D1/KV backup, a passing fingerprint check, a non-destructive Alchemy plan, and a passing post-deploy verifier.
- Pin every third-party GitHub Action by full commit SHA with the version in a trailing comment, matching upstream's workflows (for example `actions/checkout@11d5960a326750d5838078e36cf38b85af677262 # v4.4.0`). Never use a floating `@v4` in a workflow that holds deploy credentials.
- All changes go through a PR. No direct pushes to `main`, no force pushes, no branch deletion.
- Use a separate worktree. Leave the dirty `codex/dependency-upgrades-2026-10-28` checkout untouched.
- Node 22+; frozen pnpm lockfile; `pnpm ci:check`, `pnpm test:ci`, and `pnpm build` must pass on the exact deployed revision.
- D1 migrations must remain additive. Verify the `d1_migrations` table after every deploy.
- Do not add extra Cron Trigger slots on the production Cloudflare account without checking the free-plan quota. Prefer a separate Cloudflare account for staging, or no staging Worker at all.
- Secrets Store is account-scoped and write-only. Alchemy manages its values from `ENV_SELFHOST` on every deploy; the store is the runtime source, not a readable backup. The fingerprint gate is what prevents a bad `ENV_SELFHOST` from overwriting it.

## Review Focus

These are the failure modes most likely to hurt production. Each has a task that pins it:

1. **A deploy clears or changes the Google OAuth configuration.** Pinned by Task 1.3 (fail-closed preflight) and Task 1.6c (Secrets Store bindings).
2. **The custom domain is detached and Google redirect URIs stop matching.** Pinned by Task 1.4 (`CUSTOM_DOMAIN` mapping) and Task 1.7/post-deploy verification.
3. **A D1 migration re-applies or fails midway.** Pinned by Task 0.2 (backup) and Task 1.7 (migration-table verification).
4. **A fork patch is silently dropped during the upstream merge.** Pinned by Task 1.2 (patch reconciliation matrix with targeted tests).
5. **An upstream release merges green but breaks production at deploy.** Pinned by Task 2.1 (fail-closed classifier), Task 2.4 (fingerprint/preflight/plan/verify), and Task 2.7 (end-to-end drill).

## Phase 2: Automated Upstream Sync and Guarded Deployment

**How upstream ships (what the sync consumes):**

- Upstream publishes releases by tagging `main` (`pnpm release:publish` / `gh release create vX.Y.Z --target main`) and writing notes to `docs/release-notes/vX.Y.Z.md` in the same commit. Tags are the only stable boundary; `upstream/main` keeps moving after a release.
- Upstream does **not** accept external pull requests (`docs/CONTRIBUTING.md`). Fork patches cannot be upstreamed, so the four fork commits stay local and are reconciled on every merge (Task 1.2). Contribute bug reports as issues; upstream may implement them itself.
- Upstream's own deploy is `workflow_dispatch`-only, serialized, and environment-protected (`docs/maintainers/production-deployment.md`). This plan keeps that shape for production and adds an explicit risk gate for unattended low-risk runs.
- Cadence: the daily `17 6 * * *` sync keeps the fork within a day of each release. Missing several releases is fine — each merge applies the accumulated diff, and CI runs on the merged tree, so there is no need to replay intermediate tags. For an urgent security release, run `gh workflow run upstream-sync.yml -f tag=vX.Y.Z` immediately instead of waiting for the schedule.

### Task 2.2: Add the upstream sync workflow

**Files:**

- Create: `.github/workflows/upstream-sync.yml`

**Interfaces:**

- Schedule: daily `17 6 * * *` UTC.
- Manual: `workflow_dispatch` with optional `tag`.
- Permissions: `contents: write`, `pull-requests: write`, `issues: write`.
- Uses a merge identity (GitHub App or fine-grained PAT) — **not** `GITHUB_TOKEN`. No production deploy secrets.

- [ ] **Step 1: Give the workflow a merge identity that can trigger downstream runs**

This is load-bearing. GitHub suppresses workflow runs for events caused by the repository's `GITHUB_TOKEN`; a push to `main` performed by `github-actions[bot]` does **not** start `CI`, so the `workflow_run`-triggered deploy would never fire.

Pick one:

- **GitHub App (recommended).** Create an app with `contents: write`, `pull-requests: write`, `issues: write`; install it on the repo; store the app ID as variable `SYNC_APP_ID` and the private key as secret `SYNC_APP_PRIVATE_KEY`; mint a token with `actions/create-github-app-token@64ab729a6294000f5aa4a4bc0b73d1f32bc45510 # v3.3.0`. Merges are attributed to the bot, not to `GITHUB_TOKEN`, so `CI` and the deploy run normally. Pin the SHA, as every other action in this plan is pinned; a floating `@v3` on the credential-minting step is an avoidable supply-chain risk.
- **Fine-grained PAT.** Store `SYNC_TOKEN` with `contents: write`, `pull-requests: write`, `issues: write`. Simpler, but it expires and is a long-lived credential.

Use the token for: pushing the branch, opening the PR, enabling auto-merge. Keep `persist-credentials: false` on checkout and pass the token explicitly.

- [ ] **Step 2: Implement the sync job**

Steps:

1. Checkout `main` with `fetch-depth: 0` and `persist-credentials: false`.
2. `git remote add upstream https://github.com/every-app/open-seo.git`.
3. `git fetch upstream --tags --prune`.
4. Resolve the tag: input tag or the latest stable `vX.Y.Z` tag from `git tag --list 'v*' --sort=-v:refname`. Ignore pre-release suffixes and draft releases. Merge **tags, not `upstream/main`** — upstream publishes a release by tagging `main` and then may land unrelated commits, so the tag is the only stable boundary that matches the published notes. v0.1.26 is one commit behind `upstream/main` today.
5. If `git merge-base --is-ancestor "$TAG" HEAD`, exit successfully with "already synced".
6. Create branch `sync/upstream-$TAG` and check it out.
7. `git merge --no-ff "$TAG"`.
8. If conflicts:
   - push the branch with the merge identity,
   - open/update a PR labeled `upstream-sync`, `needs-resolution`,
   - open/update an issue with the conflicting files and a link to the PR,
   - stop without auto-merge.
9. If clean:
   - compute the changed files against the pre-merge merge base,
   - run `node scripts/classify-upstream-sync.mjs`,
   - push the branch with the merge identity,
   - open a PR whose body is the tag's own `docs/release-notes/$TAG.md` (exists in every upstream release tag) plus the classifier's reasons and a link to the compare view, and add a **`risk:low` or `risk:high` label**,
   - always run `gh pr merge --auto --merge` (with the same identity).

The risk label does **not** gate the merge — the operator chose to auto-merge any green PR. It is the signal the deploy workflow reads afterwards (Task 2.4) to decide whether the release needs approval. Because `risk:low` is what unlocks unattended deployment, the classifier must default to `high` for anything it does not positively recognize.

The sync workflow's own job ends as soon as auto-merge is enabled. The merge happens later, when required checks pass, and `CI` on `main` then starts the deploy workflow.

## Decisions

**Answered 2026-11-08:**

1. **Auto-merge:** any upstream sync PR that passes CI merges automatically. `main` therefore requires CI and conversation resolution, not an approving review (Task 2.3).
2. **Deploy gating:** low-risk releases deploy automatically; high-risk releases require approval in the `production` environment (Tasks 2.1, 2.4).
3. **Execution:** plan only. No code changes until the operator reviews this document.
4. **Sync unit:** merge upstream **release tags**, not `upstream/main`. Tags are the boundary that matches the published notes; upstream lands commits after a tag. Daily schedule plus manual dispatch for urgent releases.
5. **Fork patches:** upstream does not accept external PRs, so the four fork commits stay local, are documented in `docs/FORK_PATCHES.md`, and are reconciled on each merge. No upstreaming work is planned.
6. **Action pinning:** every action is pinned by full commit SHA, matching upstream's workflows. This applies to the sync workflow's app-token step too.

**Still open:**

1. **`BETTER_AUTH_SECRET` is unrecoverable.** Resolved as: keep it as an inherited Worker Secret; never rotate. The plan now depends on a deploy path that preserves it (Task 1.6c2). If the operator prefers a known secret, the only option is a deliberate rotation with re-consent for all 5 projects — that is out of scope and requires explicit approval.
2. **Secrets Store scope:** bind `GOOGLE_CLIENT_SECRET` (recovered) plus optionally `DATAFORSEO_API_KEY` and other async-read secrets. The sync-read paths (`getEnvValueSync`, used by `SamChatAgent`) cannot consume a Secrets Store binding, so a broader migration needs the async refactor extended to them.
3. **Staging:** use a separate Cloudflare account for staging, or rely on CI + the Alchemy plan + the production reviewer because the free plan has only two Cron Trigger slots?
